# Stripe TEST Checkout V2 — atomic order + stock + event receipt capture model

**Source-only; NOT DEPLOYED OR EXECUTABLE.** This is a pure DynamoDB transaction model, with no AWS SDK client, Lambda route, credentials, Stripe write, payment, inventory mutation or deployment. The new isolated Orders V2/Stock V2 sandbox tables described in `docs/CHECKOUT_V2_SANDBOX_FOUNDATION.md` do not exist yet; **do not run this plan against the original production Inventory table**.

`backend/stripe-test-atomic-capture-plan.mjs` exports `planStripeTestAtomicCapture({review,eventRow,order,stockById,now,stockTable,orderTable,eventTable})`. It uses the existing conservative `planVerifiedReservationSettlement` to assemble version- and status-conditioned physical stock decrements and the Order V2 `RESERVED/PENDING → PAID` transition, then **replaces the old requestId-keyed audit Put** with a conditional update of the *already-persisted* Stripe TEST event receipt keyed by `eventId`. These actions belong in **one** future DynamoDB `TransactWriteItems`, not separate requests.

## Transaction contract

- **Input** must be server-owned: already authenticated via the raw-body Stripe SDK, independently fetched official TEST Checkout Session, exact immutable order IDs/totals, current consistent Order V2 + Stock V2 versions, verified Stripe Tax and approved full-address carrier HMAC/quote. A caller-provided `review` object can be forged; this pure planning helper is NOT an authentication boundary and must never be exposed to a browser or HTTP caller.
- Event receipt must already exist in the deployed TEST ledger with `PENDING_REVIEW`, event fingerprint, order ID, session ID, `mode=test`, `provider=stripe` and exact positive paid audit dispositions. The order's `paymentSessionId` and `stripeSessionId` must match the same verified `cs_test_` session. Any expired reservation, missing physical stock, mismatched event or unverified shipment fails closed.
- A single proposed transaction contains (1) one conditional `StockV2` update per physical `productId` decrementing both `onHand` and `reserved` with version/quantity checks, (2) one conditional `OrdersV2` versioned `RESERVED/PENDING → PAID` update, and (3) one conditional event-ledger update `PENDING_REVIEW → SETTLED` conditioned on **eventId**, fingerprint, order/session identity and the audited dispositions. No table mutation can commit independently if any condition fails. New orders with the same checkout request ID are separately guarded by the distinct checkout request ledger.
- Every plan output contains `executable:false`, `paymentWriteAuthorized:false`, `stockWriteAuthorized:false`, `fulfillmentAuthorized:false`. It contains NO Stripe charges, shipping labels, secrets or customer PII. **Do not execute transaction plans automatically.**
- Signed replays after atomic settlement can arrive when the Order is already `PAID` rather than `RESERVED`. The replay must be cross-checked against the **paid Order V2 snapshot**, not just an event row labeled `SETTLED`. The order must retain `status=PAID` and `paymentStatus=PAID`, cite the exact `paymentEventId` and test Checkout Session IDs, have a version at or beyond `settledOrderVersion`, match the verified Stripe charge total and test mode, and be at an allowed paid fulfillment stage. The provider response must still be complete/paid with a valid payment-intent ID; settlement must be associated with a positive, reconciled payment event. Neither the signed event nor its ledger row can independently attest that Stock V2 was captured.

4. Establish TEST-mode Stripe secret storage in Secrets Manager, a new least-privilege Lambda with server-controlled provider API responses, data validation, and separate customer-data/security policies. No live Stripe payments until supported end-to-end tests.
5. Write integration tests against isolated DynamoDB transactions including races between duplicate and distinct Stripe event IDs, pending/async payments, expiry vs paid races, network timeouts, rollback and partial failure. A `SETTLED` receipt must always correspond to an atomic paid Order/Stock transaction.
6. Design and test refund/dispute reversal and shipment lifecycle independently. Setting `PAID` alone is NOT automatic authorization to fulfill an order; verify packing, shipping addresses, tracking, fraud and support policy.

This is an **inert** foundational safety improvement intended for review, not production payment activation.
